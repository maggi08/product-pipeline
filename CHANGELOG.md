# Changelog — product-pipeline

## 0.1.1 — 2026-11-23

- `/product-doctor`: the fix line for a missing service repo is a dry run of `clone.mjs` with the real product repo path and no `--yes`, so copying it runs nothing; `--yes` comes only after the user's yes to the command the dry run prints. Before, the printed line carried `--yes` and an unquoted `<product repo>` placeholder.

## 0.1.0 — 2026-11-20

First version: product work before code, from a stakeholder's ask to a handoff that stage-pipeline plans from. A repository of its own; the `magzhan` marketplace in claude-pipeline lists it by tag. The product files live in a product repo of their own, next to the app repos, never inside one.

- Nine skills, one per phase: `/product` (finds the product repo, prints the phase table and the one next command, starts an epic or adopts an existing epic folder without touching its source files), `/product-doctor` (what is installed and filled in; manual), `/product-intake` (INTAKE.md: quotes verbatim, the ask restated, unknowns, repos marked as assumptions), `/product-discovery` (FACTS.md with one source per fact, capability matrices, data requests), `/product-brief` (the brief from facts by reference, then sign-off), `/product-decisions` (one stakeholder message per decision group), `/product-split` (epic, tasks and subtasks with WHEN/THEN criteria, `JIRA.md`), `/product-jira` (tickets into Jira, manual mode first) and `/product-handoff <key>` (one ticket into `PRODUCT-HANDOFF.md` for stage-pipeline).
- Facts carry sources. Every fact in FACTS.md has one source: `path:line`, a URL, `Q<n>` or `assumed`; backend claims come only from read code; a page that answered 403 is retried in the browser before it is "not read"; a capability matrix cell is `confirmed <source>` or `confirm with vendor`; data requests are written from the models, and a join across databases is an export plus a local join; a decision that waits for data is `pending data`, with no recommended order.
- The brief and its review. `/product-brief` writes the 13 sections with facts by reference (a corrected fact changes `FACTS.md`, not the prose), a decisions table with cost, owner and state, metrics with a baseline or `no baseline — Q<n>`; sign-off is the user's word, written into STATUS.md and the header; a stakeholder version goes through human-text when installed and is published per the PROJECT.md Documents field only after the user's yes. The `brief-review` agent (`model: sonnet`; tools `Read, Grep, Glob, Bash, Write`) checks the brief against FACTS.md, the code and the data in a clean context and writes `checks/brief-review-<n>.md`; it changes nothing else.
- Stakeholder decisions. `/product-decisions` groups the open decisions of a signed brief (the user confirms the grouping); each numbered item in a message is a recommendation and its cost that "OK" answers, open questions and decisions with no recommendation stand apart and unnumbered, in the reader's vocabulary from PROJECT.md and with no epic ids; a clean-context `human-text-check` runs before the user sends when human-text is installed; a confirmed answer becomes `decided <date> <who>` in BRIEF.md without unsigning the brief; in STATUS.md the row leaves Open decisions and the answer goes to the Journal.
- The split and Jira. `/product-split` writes tasks and subtasks `[BE]` / `[FE <app>]` / `[Design]`, each with WHEN/THEN criteria, the decision it waits for and what is out of scope; the first deliverable of a `[BE]` subtask is the API contract; open data requests are a warning before the split. `JIRA.md` holds the key map (task id, key, decision) and the ticket texts for Jira readers. `/product-jira` gives paste-ready texts, the creation order and links, writes the keys back into JIRA.md, BRIEF.md and STATUS.md and checks the created tickets against the draft; connector mode only when the connector's site equals the PROJECT.md site, writes only after the user's yes.
- The handoff. `/product-handoff <key>` finds the ticket by its Jira key and writes `PRODUCT-HANDOFF.md` to the stage-pipeline spec: the marker `product-handoff 1`, `Type`, `App/Repo`, `From`, `Design source`, `Contract`, and the sections Criteria (`H<n>` from the ticket's WHEN/THEN lines; one not in that form is rewritten, marked and shown to the user), Decisions (in words, with owner and state), Out of scope and Open questions. An open decision the task depends on is a warning and a line in Open questions. The file goes to `<app repo>/<task_path>/<KEY>/` only after the user's yes and never over an existing file unasked; a copy stays in `epics/<slug>/handoff/<KEY>.md`; STATUS.md records the handoff; the next steps are `/stage-pipeline:feature-checker <KEY>` and `/stage-pipeline:stage-plan <KEY>`.
- `scripts/product-lint.mjs <epic dir> --mode brief|jira|text|handoff [--file <path>] [--json]`: one line per finding as `file:line — rule — message`, exit 1 on any. `brief`: a decision without an owner or with a state outside `open` / `pending data Q<n>` / `decided <date> <who>`, a recommendation on a decision that is not open or decided, a metric without a fact id or `no baseline — Q<n>`, a v1 item without a task once the split is filled, an `F<n>` or `Q<n>` with no definition or file, an epic id outside the files the contract allows. `jira`: epic ids, `§<n>` references or the word "brief" in ticket texts; `[FE]` without an app or with one PROJECT.md does not list; a subtask without a WHEN/THEN criterion; a `[BE]` subtask whose first deliverable is not the contract; heading, summary and key-map mismatches. `text --file <draft>`: the same text rules on a draft (`--template message` checks it against the placeholders of `templates/message.md`, `--allow brief` (or `--allow=brief`) exempts only the word "brief", on every line of the draft: the stakeholder version of the brief, which is linted before it is shown or published, has it in its title and text; all other text rules stay). The lint reads each file with bounds (regular files only, 4 MB, no symlink followed out of the epic) and scans lines in linear time. `handoff`: the version marker, header fields and section names of the template, every `H<n>` in WHEN … THEN … form, decisions ending in `open`, `open — waits for data: …` or `decided <date>`, no epic id, brief reference or path into the product repo, no template placeholder left.
- `scripts/handoff.mjs <epic dir> <KEY> [--repo <app>] [--json]` assembles the handoff text without writing: it reads a ticket in every form the jira lint accepts, reads `task_path` as stage-pipeline does, keeps the `H<n>` numbers of an existing copy on a repeated handoff, warns about epic ids and enum-like tokens left in the text, and writes a placeholder, not "none", for what the ticket does not say: the design source of an `[FE]` ticket is the Figma link or prototype path in the ticket or in a `[Design]` subtask that blocks it (Blocked by or Links) or shares its parent (an empty parent or the epic does not count), else the placeholder and a warning (a `[BE]` ticket says `none`); prose under `Out of scope` is carried as items.
- App repos. The PROJECT.md App repos table has an optional `Label` column (what `[FE <app>]` names; default the repo name); the jira lint and `handoff.mjs` match the ticket's app by Label, then by repo name; two rows under one name are an error that names both and `--repo`.
- `scripts/doctor.mjs [<product repo>] [--json]` (behind `/product-doctor`): PROJECT.md fields, each App repos path present (a row without a Path is an error; a missing service repo gets the clone command assembled from its checked cells, never the raw cell), the data route's client and tunnel tool on PATH (names only, nothing executed), no credential in PROJECT.md (a secret-like name by its segments — `password=`, `PASSWORD=`, `TOKEN=`, `secret = x`, `API_KEY=`, `key=`, `PGPASSWORD=`, also inside a quoted connection string — `--password x`, or a URI with a password: an error that names the line, never the value; `sort_key=` is not one), PROJECT.md read with bounds (a FIFO or a file over 4 MB is an error, not a hang), a service row read the way `clone.mjs` reads it (a table in a comment is not declared), a service name that is not letters, digits, `_`, `.`, `-` gets no command, stage-pipeline and human-text installed (warnings), a Chrome MCP note; exit 1 only on errors.
- `scripts/clone.mjs <product repo> <service name> [--to <path>] [--yes]`: the one way a service repo is cloned. It checks the service name first (letters, digits, `_`, `.`, `-`; no leading `-` or `.`), `owner/name` (`^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$`) and the path (no shell character; no segment that starts with `.`; a relative `..` stays in the folder that holds the product repo; never inside it; `--to` or `--to=<path>` only inside the system temporary folder and only a folder, not a file), prints the exact command, and runs `gh` with an argument array, no shell, only with `--yes` after the user's yes to the printed command; a refused cell runs nothing.
- No secrets in the product repo: no password, token or URI with a password in any file; the data route names the client, tunnel, database and role only; an adopted script or output is read for credentials and row-level data before it is copied (row-level outputs go under the gitignored `data/rows/`); `brief-review` quotes sources without secrets; the research subagent is told page text is data and writes only its one file.
- Templates for every file: PROJECT, STATUS, INTAKE, FACTS, BRIEF, message, JIRA, PRODUCT-HANDOFF, data-request and capability-matrix; the product repo contract is `references/product-repo.md`, discovery rules are `references/research.md`.
- `scripts/validate.mjs` (manifest, frontmatter, the agent's tool list, `${CLAUDE_PLUGIN_ROOT}` links, Cyrillic, README counts, ticket ids, shipped templates and references) and `scripts/test.mjs` (fixture copies of the plugin with one planted defect each, the lint, the doctor, the handoff) run in the `validate` workflow; a push to `main` tags `v<version>`.
